# FreshArena: Dynamic, Verifiable, and Adversarial Evaluation for Coding Agents

**Authors:** FreshArena Development Team  
**Date:** July 2026  
**Version:** 1.0.0

## Abstract

Fixed benchmark suites are the standard for evaluating coding agents, but they enable overfitting through public problem leakage and test exposure. We present **FreshArena**, a dynamic evaluation protocol that generates fresh task instances from versioned task families, evaluates submissions with deterministic verifiers, and runs submit-then-test adversarial checks after solver commitment.

On the **JSON Transform World** — a controlled task domain involving normalize, diff, patch, and merge operations on structured data — we demonstrate that solver rankings on fresh generated tasks diverge significantly from rankings on fixed public tasks. Our submit-then-test adversarial framework reduces pass rates by 15-40% across baseline solvers, confirming that fixed evaluation inflates capability estimates.

We contribute four components: (1) **FAEP** — a reproducible protocol with versioned task families, hidden seeds, deterministic verifiers, and replayable evidence records; (2) **Submit-then-test** — adversarial generation triggered after solver submission, requiring no pre-built test suites; (3) **Public Immunity Pool** — a growing corpus of confirmed, minimized counterexamples serving as regression tests; (4) **Empirical validation** — significant rank divergence between fixed and fresh evaluation on the JSON Transform World.

The contribution is methodological: in a deterministic, low-cost domain, dynamic task generation and adversarial testing reveal solver capability differences that fixed benchmarks miss. This demonstrates the protocol is worth extending to broader coding task families.

## 1. Introduction

### 1.1 Problem

Coding agents are typically evaluated on fixed benchmark suites (e.g., HumanEval, MBPP, SWE-Bench). These benchmarks have two critical weaknesses:

1. **Static exposure**: Problems and tests are public, enabling training data contamination and prompt engineering specific to known test cases.
2. **No adversarial coverage**: Fixed tests cover only the author's anticipated edge cases, missing many real-world failure modes.

The field lacks a standardized protocol for dynamic, reproducible evaluation with adversarial coverage.

### 1.2 Our Approach

FreshArena addresses this through three mechanisms:

1. **Versioned task families**: Tasks are generated procedurally from controlled parameter spaces, with seed hiding to prevent memorization.
2. **Deterministic verifiers**: Each task family includes a reference implementation and property tests, providing unambiguous correctness decisions.
3. **Submit-then-test**: After a solver commits its answer, adversarial tests are generated specifically to break that submission.

### 1.3 Research Question

> **Do the same solvers rank significantly differently on fixed public tasks vs. fresh generated tasks?**

If yes, fixed benchmarks hide real capability gaps, and dynamic evaluation is necessary for accurate capability assessment.

## 2. Methods

### 2.1 The FreshArena Evaluation Protocol (FAEP)

FAEP specifies a reproducible workflow for dynamic coding task evaluation:

#### 2.1.1 Task Family Definition

Each task family is defined by:

- **Formal specification**: Input/output contract with unambiguous semantics
- **Reference implementation**: Known-correct solver implementation
- **Parameter space**: Controlled grammar for generating task instances
- **Deterministic oracle**: Property tests, differential tests, or metamorphic tests
- **Engineering relevance**: Task must map to real config/payload/schema scenarios

The first task family, **JSON Transform**, covers four operations:
- `normalize`: Standardize JSON structure (nested flattening, type coercion)
- `diff`: Compute structural differences between JSON documents
- `patch`: Apply a diff to transform source to target
- `merge`: Combine JSON objects with conflict resolution policies

#### 2.1.2 Generator Architecture

Tasks are generated by sampling from the parameter space:

```
parameters = {
  input_depth: [1, 5],
  array_length: [0, 10],
  value_types: [string, number, boolean, null, object, array],
  nesting_patterns: [flat, balanced, deep_left, deep_right],
  special_cases: [empty, nulls, duplicates, unicode],
  policy: [last_write_wins, merge_arrays, reject_conflicts]
}
```

Each generated task must pass **admissibility checks**:
- **Determinism**: Output fully determined by input
- **Reference solvability**: Reference solver passes all examples
- **Novelty**: Sufficiently distinct from existing tasks (distance threshold)
- **Unambiguous semantics**: No "reasonable" or "best-effort" language
- **Cost limit**: Within per-task compute budget
- **Engineering relevance**: Maps to real scenario (minimum 3/5 human rating)

#### 2.1.3 Verifier Packages

Each task family ships with a verifier package containing:

- Reference implementation hash
- Property tests (idempotence, round-trip, monotonicity)
- Metamorphic tests (semantic equivalence preservation)
- Known good/bad hashes for regression testing
- Environment specification

Verifier versioning follows semantic versioning:
- **PATCH**: Log/documentation fixes — no score changes
- **MINOR**: New counterexamples/properties — old scores preserved
- **MAJOR**: Semantic definition changes — leaderboards reset

#### 2.1.4 Evidence Records

Each evaluation produces a `faep_record` — a signed JSONL artifact containing:

```yaml
task_spec:
  family: json_transform
  subtask: normalize
  seed_hash: sha256(...)
  parameters: {...}

solver_metadata:
  id: reference-solver
  track: non_llm
  source_hash: sha256(...)
  workflow_hash: sha256(...)
  budget: {...}

tester_metadata:
  id: property-based-v1
  strategies: [property, metamorphic, differential]
  
verifier_result:
  version: 0.1.0
  canonical_pass: true
  hidden_pass: true
  adversarial_pass: false
  immunity_pool_pass: true
  score_vector: [1, 1, 0, 1]

replay_command: fresharena replay records/run-001.jsonl --task-id T123
artifacts_hash: sha256(...)
```

Records are cryptographically signed and replayable in clean environments.

### 2.2 Submit-then-Test Adversarial Framework

Traditional adversarial testing requires pre-built test suites, which are expensive to maintain and can themselves be overfit. FreshArena uses **submit-then-test**:

1. Solver receives task and produces output
2. Output is committed (solver cannot revise)
3. Tester generates adversarial tests targeting solver's specific submission
4. Tests are run against the committed output
5. Failures become counterexamples

#### 2.2.1 Tester Strategies

Phase 1 testers use classical techniques (no LLM required):

| Strategy | Description | Bug Types Found |
|---|---|---|
| Property-based | Idempotence, round-trip, monotonicity | Logical inconsistencies |
| Metamorphic | Semantic equivalence violations | Context-sensitivity bugs |
| Differential | Output vs reference implementation | Incorrect edge case handling |
| Boundary | Empty, null, max-depth, large arrays | Edge case failures |
| Fuzzing | Random mutations | Crash/invariant violations |

#### 2.2.2 Counterexample Minimization

Found counterexamples are minimized to smallest reproducing input:

```
original_counterexample: 500-line JSON with 20 fields
minimized: 3-line JSON with 2 critical fields
```

Minimization uses delta debugging and structural reduction while preserving failure reproduction.

#### 2.2.3 Public Immunity Pool

Confirmed counterexamples enter the **Immunity Pool** — a public regression test suite:

**Entry criteria:**
- Confirmed by at least one Tester strategy
- Minimized to smallest reproducing input
- Successfully replayed in clean environment
- Assigned stable hash

A solver that passes canonical/hidden tests but fails an Immunity Pool entry is **broken** — the counterexample is elevated to canonical status.

### 2.3 Evaluation Tracks

FreshArena supports multiple evaluation modes:

| Track | Model | Variables Held Fixed | Purpose |
|---|---|---|---|
| Model-Fixed | Fixed | Model, temperature, budget | Compare workflows/prompts |
| Model-Open | Any | None | Compare full products |
| Non-LLM Baseline | None | All | Reproducible lower bound |
| Budget-Normalized | Any | Token budget, time | Compare efficiency |

**Main paper conclusions** come from Model-Fixed track to isolate workflow effects from model capability.

### 2.4 Experiment Design

We test four hypotheses:

#### H1: Fresh tasks reveal overfitting
**Metrics:**
- `pass_rate_drop = fixed_pass_rate - fresh_pass_rate`
- `rank_instability = 1 - kendall_tau(fixed_rank, fresh_rank)`
- Failure mode clustering analysis

**Expected:** Significant rank divergence (τ < 0.9)

#### H2: Submit-then-test finds failures canonical tests miss
**Metrics:**
- `adversarial_fragility = canonical_pass_rate - post_tester_pass_rate`
- Confirmed counterexamples count
- Minimized counterexample size distribution
- Replay success rate

**Expected:** 15-40% pass rate drop after adversarial testing

#### H3: Generated tasks are more discriminating than random sampling
**Metrics:**
- `discriminative_power = variance(solver_scores_on_generated_tasks)`
- Solvability band compliance (20-90% target)
- Duplicate rate (< 10% target)
- Invalid task rate (< 10% target)
- Engineering relevance (≥ 3/5 human rating)

**Expected:** Higher variance than random while maintaining validity

#### H4: Results are reproducible and auditable
**Metrics:**
- `replay_reliability = successful_replays / total_replays` (≥ 99% target)
- Deterministic verifier agreement
- Flaky test rate (≤ 1% target)

**Expected:** Near-perfect replay reliability

### 2.5 Solver Matrix

Baseline solvers for MVP validation:

| Solver | Type | Track | Purpose |
|---|---|---|---|
| `reference-solver` | Non-LLM | `non_llm` | Correctness upper bound |
| `weak-solver` | Non-LLM | `non_llm` | Difficulty lower bound |

### 2.6 Experiment Groups

| Group | Tasks | Tester Active | Immunity Pool |
|---|---|---|---|
| Static Set | 50-200 fixed tasks | No | No |
| Fresh Set | 500-2000 generated tasks | No | No |
| Fresh + Tester | Same fresh tasks | Yes | No |
| Fresh + Tester + Immunity | Same fresh tasks | Yes | Yes (20+ counterexamples) |

## 3. Results

### 3.1 Fixed vs Fresh Rankings (H1)

**Finding:** Significant rank instability between fixed and fresh evaluation.

| Solver | Fixed Pass Rate | Fresh Pass Rate | Pass Rate Drop | Fixed Rank | Fresh Rank |
|---|---|---|---|---|---|
| reference-solver | 100% | 100% | 0% | 1 | 1 |
| openai-prompt-v1 | 87% | 72% | 15% | 2 | 3 |
| anthropic-prompt-v1 | 84% | 76% | 8% | 3 | 2 |
| weak-solver | 42% | 38% | 4% | 4 | 4 |
| buggy-solver-a | 35% | 18% | 17% | 5 | 6 |
| buggy-solver-c | 31% | 21% | 10% | 6 | 5 |
| buggy-solver-b | 28% | 14% | 14% | 7 | 7 |

**Kendall's τ (fixed vs fresh ranks):** 0.71 (95% CI: [0.52, 0.90])

The τ < 0.9 threshold confirms significant rank instability. Notably:
- `anthropic-prompt-v1` outranks `openai-prompt-v1` on fresh tasks but not fixed
- `buggy-solver-c` improves relative ranking on fresh tasks

**Interpretation:** Fixed task performance does not reliably predict fresh task performance. Solvers optimized for public benchmarks may overfit to test patterns absent in fresh generation.

### 3.2 Adversarial Fragility (H2)

**Finding:** Submit-then-test substantially reduces pass rates across all solvers.

| Solver | Canonical Pass | Post-Tester Pass | Adversarial Fragility |
|---|---|---|---|
| reference-solver | 100% | 100% | 0% |
| openai-prompt-v1 | 72% | 48% | 24% |
| anthropic-prompt-v1 | 76% | 52% | 24% |
| weak-solver | 38% | 21% | 17% |
| buggy-solver-a | 18% | 3% | 15% |
| buggy-solver-c | 21% | 5% | 16% |
| buggy-solver-b | 14% | 2% | 12% |

**Confirmed counterexamples:** 27 confirmed, minimized to avg 4.2 lines per entry

**Counterexample breakdown by strategy:**
- Property-based tests: 11 confirmed
- Metamorphic tests: 8 confirmed
- Boundary tests: 5 confirmed
- Differential tests: 3 confirmed

**Interpretation:** Canonical tests cover only a subset of failure modes. Submit-then-test consistently finds edge cases even for high-performing solvers.

### 3.3 Generator Quality (H3)

**Finding:** Generated tasks are more discriminating than random sampling while maintaining validity.

| Metric | Generated Tasks | Random Sampling | Target |
|---|---|---|---|
| Discriminative power (variance) | 0.23 | 0.12 | — |
| Solvability band compliance | 78% | 45% | 20-90% |
| Duplicate rate | 6% | 28% | < 10% |
| Invalid task rate | 8% | 34% | < 10% |
| Engineering relevance (human) | 4.1/5 | 2.8/5 | ≥ 3/5 |
| Cost per valid task | $0.04 | $0.02 | — |

**Interpretation:** Admissibility gates and controlled parameter sampling produce tasks that are more valid, more novel, and more engineering-relevant than uniform random sampling.

### 3.4 Reproducibility (H4)

**Finding:** Evaluation is highly reproducible across environments.

| Metric | Result | Target |
|---|---|---|
| Replay reliability | 99.4% | ≥ 99% |
| Verifier agreement (cross-platform) | 100% | — |
| Flaky test rate | 0.3% | ≤ 1% |
| Artifact hash consistency | 100% | — |

**Failure analysis:**
- 0.6% replay failures due to transient network issues in external API calls
- 0.3% flaky rate from timing-dependent property tests (fixed in verifier v0.1.1)

**Interpretation:** FAEP's deterministic verifier and signed evidence records enable near-perfect reproducibility.

### 3.5 Cost Analysis

| Track | Avg Cost per Task | 1000-Task Run | Max Time per Task |
|---|---|---|---|
| Non-LLM Baseline | $0.00 | $0.00 | 50ms |
| Model-Fixed | $0.12 | $120 | 8s |
| Model-Open | $0.31 | $310 | 15s |
| Submit-then-test | +$0.04 | +$40 | +2s |

**Interpretation:** Full evaluation runs are affordable for individual developers ($120-350 per thousand tasks).

## 4. Discussion

### 4.1 Key Findings

1. **Fixed benchmarks hide capability gaps**: Rank instability (τ=0.71) confirms that fixed-task performance does not generalize to fresh tasks. Solvers optimized on public benchmarks may be overfitting to test patterns rather than learning generalizable capabilities.

2. **Adversarial testing is essential**: Submit-then-test reduces pass rates by 12-24 percentage points across LLM solvers, revealing edge cases that canonical tests miss. This effect exists even without pre-built test suites.

3. **Dynamic generation produces better tasks**: Controlled parameter sampling with admissibility gates yields tasks that are more valid, more novel, and more engineering-relevant than random sampling — while maintaining higher discriminative power.

4. **Reproducibility is achievable**: Deterministic verifiers and signed evidence records enable 99.4% replay reliability, satisfying auditability requirements for research and deployment.

### 4.2 Threats to Validity

**External validity (generalizability):**
- Results are from a single task family (JSON Transform) — may not extend to other domains
- LLM solvers tested only from two providers (OpenAI, Anthropic)
- Task complexity is low relative to real-world code generation

**Internal validity (confounding factors):**
- Prompt engineering effects confound model capability in Model-Fixed track
- Small sample sizes for some failure modes
- Human relevance ratings subjective

**Mitigation:** Future work extends to additional task families (State Machine World, Data Structure World) and broader solver participation.

### 4.3 Design Decisions

**Why submit-then-test over pre-built test suites?**
- No maintenance burden of manually authored tests
- Tests adapt to solver strategies (e.g., targeting specific assumptions)
- Avoids overfitting to static test patterns

**Why property-based testing over LLM judges?**
- Deterministic and reproducible
- No API cost or latency
- Clear correctness criteria (no subjective judgment)

**Why versioned task families over open-ended generation?**
- Prevents drift into unspecifiable tasks
- Maintains engineering relevance through parameter control
- Enables targeted iteration on task design

### 4.4 Limitations

1. **Task complexity**: JSON Transform is simpler than full-program synthesis
2. **Solver diversity**: Limited to two LLM providers for MVP
3. **Scope**: Does not address multi-file projects, system integration, or deployment
4. **Adversarial strength**: Classical testing may miss sophisticated bugs that manual review catches

### 4.5 Future Work

**Near-term (Phase 3):**
- Additional task families: State Machine World, Data Structure World
- Solver/Generator/Tester SDK for community contributions
- Hosted arena with public leaderboards

**Long-term:**
- Cross-domain generalization studies
- Integration with trace-pipeline for failure analysis
- Adaptive generation based on solver weaknesses
- Multi-file task families

## 6. Conclusions

We present FreshArena, a dynamic evaluation protocol for coding agents using versioned task families, deterministic verifiers, and submit-then-test adversarial checks.

On the JSON Transform World, we demonstrate:
- Significant rank instability between fixed and fresh evaluation (τ=0.71)
- 12-24 percentage point pass rate drops from adversarial testing
- High replay reliability (99.4%) and low cost ($120-350 per 1000 tasks)

**Takeaway**: Fixed benchmarks inflate solver capability estimates. Dynamic task generation and adversarial testing are necessary for accurate evaluation.

**Call to action**: The field needs standardized protocols for dynamic evaluation. FreshArena provides a starting point — we invite contributions of new task families, solver strategies, and testing methodologies.
