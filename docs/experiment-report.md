## Executive Summary

This document reports on the FreshArena experiment, which evaluates coding agent generalization capabilities through dynamically generated tasks and adversarial testing. The experiment tests four core hypotheses:

1. **H1 — Fresh tasks reveal overfitting**: Same solvers rank differently on fixed vs fresh tasks
2. **H2 — Submit-then-test finds failures**: Adversarial tests find bugs canonical tests miss  
3. **H3 — Generators outperform random sampling**: Generated tasks have higher discriminative power
4. **H4 — Results are reproducible and auditable**: Full replay capability across environments

---

## 1. Methodology

### 1.1 Research Hypotheses

#### H1 — Fresh tasks reveal overfitting

**Hypothesis**: The same solvers rank significantly differently on fixed public tasks vs. fresh generated tasks, revealing overfitting to public benchmarks.

**Metrics**:
- `pass_rate_drop` — Per-solver pass rate difference between fresh and fixed tasks
- `fresh_generalization_gap = fixed_pass_rate - fresh_pass_rate`
- `rank_instability = 1 - kendall_tau(fixed_rank, fresh_rank)` — Measures ranking correlation
- **Failure mode clustering**: Analyze whether solvers fail in structured patterns or random ways

**Statistical Test**: Kendall's τ (tau) correlation coefficient to measure rank agreement between fixed and fresh task rankings. A τ < 0.9 indicates significant rank instability.

#### H2 — Submit-then-test finds failures

**Hypothesis**: After solver submission, adversarial tests generated by the Tester significantly reduce pass rates, revealing hidden bugs.

**Metrics**:
- `canonical_only_pass_rate` — Pass rate on initial verification tests only
- `canonical_plus_adversarial_pass_rate` — Pass rate after Tester runs
- `adversarial_fragility = canonical_pass_rate - post_tester_pass_rate`
- **Newly confirmed counterexamples count** — Unique failing inputs found
- **Minimized counterexample size distribution** — Complexity of found counterexamples
- **Replay success rate** — Confirm found counterexamples are deterministic

**Statistical Test**: Paired t-test comparing `canonical_pass_rate` vs `post_tester_pass_rate` per solver to confirm significant drops.

#### H3 — Generators produce more discriminating tasks

**Hypothesis**: Generated tasks have higher per-solver variance in pass rates than pure random tasks, while staying within solvability bounds.

**Metrics**:
- `discriminative_power = variance(solver_scores_on_generated_tasks)`
- **Solvability band compliance** — Target 20%–90% pass rate range
- **Duplicate rate** — Target < 10% semantically equivalent tasks
- **Invalid task rate** — Target < 10% unsolvable or malformed tasks
- **Engineering relevance score** — Human sampling, target ≥ 3/5
- **Cost per valid task** — API and compute costs

**Statistical Test**: F-test comparing variance of solver scores on generated tasks vs random tasks. Higher variance indicates better discrimination.

#### H4 — Results are reproducible and auditable

**Hypothesis**: Any evaluation run can be replayed in a clean environment and produce identical scores.

**Metrics**:
- `replay_reliability = successful_replays / total_replays` — Target ≥ 99%
- **Deterministic verifier agreement** — Cross-environment consistency
- **Artifact hash consistency** — Cryptographic verification of outputs
- **Environment pinning completeness** — Full dependency capture
- **Flaky test rate** — Target ≤ 1%

**Validation**: Full re-run of experiment in clean Docker containers with hash verification.

### 1.4 Task Family: JSON Transform

The JSON transform task family consists of four subtasks:

1. **Normalize**: Clean and standardize JSON structure (remove extra whitespace, sort keys, handle type coercion)
2. **Diff**: Compute semantic differences between two JSON documents (ignoring ordering, handling nested structures)
3. **Patch**: Apply a diff patch to transform one JSON document into another
4. **Merge**: Combine multiple JSON documents with conflict resolution strategies

Each generated task specifies:
- Input JSON structure (nested objects, arrays, mixed types)
- Subtask type and parameters
- Expected output specification
- Difficulty category (trivial, easy, medium, hard, expert)

### 1.5 Verification Protocol

All submissions are verified through:

1. **Canonical Tests** — Basic correctness checks (5–10 test cases per task)
2. **Property-Based Testing** — Generative testing with 100+ random inputs
3. **Adversarial Testing** — Tester-generated edge cases targeting:
   - Boundary conditions (empty, null, very large inputs)
   - Type confusion scenarios
   - Nested structure edge cases
   - Unicode and encoding issues
   - Performance edge cases

**Success Criteria**: All tests must pass deterministically across 3+ replay runs.

## 4. Statistical Analysis

### 4.1 Rank Correlation (H1)

**Method**: Kendall's Tau (τ) rank correlation coefficient

**Purpose**: Measure agreement between solver rankings on static vs fresh tasks

**Interpretation**:
- τ = 1.0: Perfect rank agreement
- τ = 0.0: No correlation
- τ = -1.0: Perfect rank disagreement
- **Target**: τ < 0.9 indicates meaningful rank instability (overfitting detected)

**Formula**:
$$
\tau = \frac{\text{concordant pairs} - \text{discordant pairs}}{\binom{n}{2}}
$$

**Statistical Test**: Permutation test for significance (p < 0.05)

### 4.2 Adversarial Fragility (H2)

**Method**: Paired sample t-test (canonical vs post-tester pass rates per solver)

**Purpose**: Determine if Tester finds statistically significant failures

**Effect Size**: Cohen's d for magnitude of fragility

**Formula**:
$$
d = \frac{\mu_{\text{canonical}} - \mu_{\text{post-tester}}}{\sigma_{\text{pooled}}}
$$

**Interpretation**:
- d = 0.2: Small effect
- d = 0.5: Medium effect  
- d = 0.8+: Large effect

### 4.3 Discriminative Power (H3)

**Method**: F-test for equality of variances

**Purpose**: Compare score variance between generated and random tasks

**Hypothesis**:
- H₀: σ²_generated = σ²_random
- H₁: σ²_generated > σ²_random

**Test Statistic**:
$$
F = \frac{s^2_{\text{generated}}}{s^2_{\text{random}}}
$$

**Interpretation**: Higher variance → better discrimination between solver capabilities

### 4.4 Confidence Intervals

All pass rates reported with 95% Wilson score intervals (appropriate for binomial proportions):

$$
\text{CI} = \frac{\hat{p} + \frac{z^2}{2n} \pm z\sqrt{\frac{\hat{p}(1-\hat{p})}{n} + \frac{z^2}{4n^2}}}{1 + \frac{z^2}{n}}
$$

Where $\hat{p}$ is observed pass rate, $n$ is sample size, $z = 1.96$ for 95% CI.

### 4.5 Multiple Comparison Corrections

When testing multiple solvers/hypotheses simultaneously, apply:

- **Bonferroni correction**: Divide α by number of comparisons
- **False Discovery Rate (FDR)**: Benjamini-Hochberg procedure for exploratory analysis

### 4.6 Power Analysis

**Minimum Sample Size** (per solver, per group):

For detecting effect size d = 0.5 (medium) with 80% power at α = 0.05:

$$
n_{\text{required}} \approx 64 \text{ tasks}
$$

Current design (500–2000 fresh tasks) provides > 99% power for medium effects.

## 6. Threats to Validity

### 6.1 Internal Validity

- **Task generation bias**: Generator may produce tasks favoring certain solver approaches
  - *Mitigation*: Random seed variation, cross-validation with human-designed tasks
- **Verifier correctness**: Bugs in verification could produce false failures
  - *Mitigation*: Property-based testing of verifier itself, human inspection of counterexamples
- **Solver version drift**: LLM API changes during experiment
  - *Mitigation*: Fixed model versions, request freezing, replay verification

### 6.2 External Validity

- **Task family generalization**: JSON transforms may not represent all coding tasks
  - *Mitigation*: Future expansion to additional task families
- **Solver representativeness**: Limited solver set may not reflect full agent ecosystem
  - *Mitigation*: Include diverse solver archetypes, future expansion
- **Temporal validity**: Results may not generalize to future model versions
  - *Mitigation*: Clear documentation of model versions, periodic re-running

### 6.3 Construct Validity

- **Pass rate as capability metric**: May not capture all dimensions of agent quality (efficiency, robustness, explainability)
  - *Mitigation*: Track multiple metrics (cost, latency, counterexample diversity)
- **Fresh vs fixed dichotomy**: Static tasks may have been seen during training
  - *Mitigation*: Document task provenance, use post-training-cutoff tasks
